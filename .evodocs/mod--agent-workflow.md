# purpose

The `agent-workflow` module defines the repo-local `intentmill-ops` workflow that turns a configured project issue into reviewed planning artifacts. It is not application runtime TypeScript, but it is part of the application's operational behavior because the IntentMill server launches Codex with instructions to load this workflow and run the full planning sequence for a selected issue. The workflow is the contract between a UI-triggered `Generate Plan` action, the target project worktree, target-project requirement tooling, and the server code that later persists successful results.

Its main purpose is to keep AI planning runs bounded and repeatable. A run begins with a project key or alias and a Linear-style issue id, resolves the configured target repository, prepares a clean issue worktree, refreshes the target project's ticket context, generates local IntentMill artifacts, and reviews each artifact before any downstream stage is allowed to proceed. The module also protects the system from common agent hazards: using the wrong repository root, writing to a dirty worktree, exposing personal local paths, mixing requirements with solutions, inventing database contracts, skipping acceptance criteria, or treating a correctly formatted but shallow artifact as ready.

For future coding work, this module matters because changes to its rules affect both agent behavior and server persistence. If a capability's output shape changes, the server-side artifact reader may fail. If the gate semantics are weakened, the UI can show stale or low-quality planning fields. If worktree or path rules are loosened, the server may commit unexpected files or publish local machine details.

# structure

The module is organized around a top-level skill contract and capability reference files. The top-level skill defines trigger scope, required inputs, shared validation, and the list of capabilities. It requires every operation to receive both a configured `project` and an uppercase issue id shaped like `ENG-123`. It also establishes the first source of truth: project keys and aliases are resolved from `ssot-config.json`, not guessed from user wording or repository names.

The first responsibility area is workspace preparation. Capability 1 creates or reuses an issue worktree under `.workspace/<project-key>--<ISSUE-ID>`. It treats `.workspace/<project-key>` as the base clone, updates that base from the configured default branch, and then uses the issue id as the branch name for the sibling worktree. Its dirty-state policy is deliberately narrow: dirty files limited to the current ticket's `.t2p/tickets/<ISSUE-ID>/` artifacts may be refreshed by the planning flow, but source changes, other ticket artifacts, or unrelated untracked files block the run. This boundary is important because later server code may commit and push planning artifacts after a successful gate.

The second responsibility area is target-project ticket context. Capability 2 requires the issue worktree to contain the target project's own t2p skill. It does not manually create raw requirement files when that project skill exists. Instead, it delegates to `t2p-new` when the ticket directory is absent and `t2p-req` when it already exists. This keeps Linear-derived or project-specific requirement capture inside the target project's workflow rather than duplicating that logic in IntentMill.

The generation responsibilities are split by artifact role. Capability 3 produces `im-req-engineered.md` and `im-req-summarized.md`, translating raw ticket sources into product requirement, engineering context, scope, behavioral requirements, regression boundaries, and open risks. Capability 4 produces `im-ac.md` as numbered, independently verifiable acceptance criteria. Capability 5 produces `im-solution.md` as developer-facing implementation guidance with overview, details, and numbered steps. Capability 6 produces `im-estimation.md` with exactly one development mode, one numeric hour value, and one concise rationale.

The review responsibility is centralized in capability 11. It can review one or more targeted artifacts immediately after a generation stage, or all generated refs at the end of the flow. The top-level cap7 orchestrator runs capabilities 1 through 6 in order and inserts cap11 after every generation stage. A `revise` result requires the owning generation capability to rewrite the failed artifact before the next capability can proceed. This review loop is semantic: it checks grounding, usefulness, scope discipline, artifact separation, path safety, and downstream fitness rather than only headings and field names.

# flows

The backend-triggered flow starts when the server builds a Codex prompt for a `generate-issue-plan` action. That prompt supplies the project and issue id, tells Codex to work from the IntentMill repository root, loads this repo-local workflow, and asks it to run cap7. The workflow first resolves project configuration and normalizes inputs. It then ensures the base target repository exists under `.workspace/`, updates it from the configured default branch, creates or attaches the issue worktree, checks dirty state, and rebases the issue branch onto the latest remote default branch.

After the worktree is ready, the workflow switches operational context to the issue worktree. It requires the target project t2p skill, then either initializes or refreshes `.t2p/tickets/<ISSUE-ID>/`. From that point, generated planning artifacts stay under the ticket's `refs` directory. The workflow reads raw requirement inputs, relevant target-project evodocs, and targeted code evidence before producing the engineered requirement and summary. It immediately runs a targeted quality gate for those two artifacts. If they are not grounded enough, contradict source evidence, or fail role separation, cap3 must be rerun before acceptance criteria are generated.

Acceptance criteria generation consumes the engineered requirement rather than raw notes alone. The criteria must be observable, numbered, bounded to twenty items, and regression-aware. After cap4 writes `im-ac.md`, another targeted cap11 review decides whether the criteria can drive downstream implementation and testing. The solution stage then consumes the requirement and acceptance criteria and produces a concrete implementation path without code snippets or test procedure. The solution's special database discipline matters when a ticket touches durable state: undefined tables or stores must be decision gaps, while existing constraints and compatibility-sensitive values must be inspected before modification. This solution also receives its own targeted gate.

Estimation is the final generation stage. It reads the requirement, AC, solution, and summary, classifies solution steps and acceptance criteria internally, applies risk adders, chooses one of `agent`, `agent-led`, or `human-led`, and writes a compact three-field estimate. The estimate is gated as well, mainly for shape, single-mode discipline, rationale grounding, and path safety. Only after cap6 passes targeted review does cap7 run cap11 in all mode over the final artifact set.

The workflow itself stops at artifact creation and review. It does not write IntentMill database fields, modify Linear, create a PR, or commit/push. In the backend-triggered path, the server takes over after Codex exits. The server reads the final `im-gate.md` decision, parses generated refs, commits and pushes only the current ticket artifact directory when needed, and writes the planning fields into the local `issues` table. That separation means the workflow must make its final artifacts precise enough for server automation but must not perform the server's persistence work itself.

# module-relationships

The primary upstream consumer and caller is the Codex run service in the runtime server. That service owns process spawning, run directories, stdout/stderr capture, timeout handling, status recovery, and final persistence. `agent-workflow` owns the instructions that the spawned Codex process follows inside the target issue worktree. A change to the workflow can therefore change the meaning of a successful process exit even though the runner code has not changed.

The workflow depends on `ssot-config.json` for project resolution. The configured project key, aliases, repository URL, and default branch determine which base clone is used and where the issue worktree is created. It also depends on Git state in `.workspace/<project-key>` and `.workspace/<project-key>--<ISSUE-ID>`. The module's dirty-state rules protect the later Git sync path in the Codex run service, which refuses to commit non-ticket changes after a successful run.

The target project t2p skill is another required downstream/upstream relationship. `agent-workflow` delegates raw ticket initialization and refresh to that target-project skill, then consumes the resulting `.t2p/tickets/<ISSUE-ID>/` sources. This keeps project-specific Linear capture, attachment handling, or requirement normalization out of IntentMill's workflow rules. If the target project lacks the skill, capability 2 stops rather than inventing a parallel requirements process.

The module produces artifacts consumed by issue persistence. `im-req-summarized.md`, `im-solution.md`, and `im-ac.md` are stored as text fields. `im-estimation.md` is parsed into a structured estimation object with a constrained development mode, numeric hours, and rationale. `im-gate.md` is not merely a human report; it is part of the safety signal that determines whether the server should persist the generated planning fields. Shape drift in cap6 or gate wording can break or mislead this runtime path.

The workflow also relates to Linear and Git remotes, but through controlled boundaries. Linear is a source of issue context through prior sync and target-project t2p behavior; this module forbids direct Linear mutation. Git remotes are used to update base branches and issue worktrees, while final commit and push are server-owned in the backend-triggered path. The workflow's job is to leave a clean, reviewable artifact set under the current ticket path so that the server can safely perform its limited Git operation.

# constraints

The strongest invariant is context discipline. Shared checks must run before every capability: the current operation starts from the IntentMill root, resolves the project from live configuration, and validates the issue id. Issue-specific generation then happens in the issue worktree, not in the IntentMill root and not in the base target clone. Violating that boundary can write `.t2p` artifacts into the wrong repository or make the server look for refs in a path that was never prepared.

Worktree cleanliness is part of data safety. Capability 1 can tolerate refreshable planning artifacts for the current issue, but source changes or unrelated files must block the run. The later server persistence path commits only `.t2p/tickets/<ISSUE-ID>/`; if the workflow allows unrelated changes to accumulate, a successful generation can leave hidden work behind or fail late during Git sync.

Artifact role separation must be preserved. Requirements explain what and why, acceptance criteria define observable completion, solution explains the implementation path, estimation gives the execution mode and hours, and gate review decides readiness. Putting test commands into requirements, solution steps into AC, code snippets into solution, or scoring tables into estimation weakens downstream automation because each later stage assumes a specific kind of input.

Semantic gates are mandatory. A targeted `revise` is not advisory; the owning capability must regenerate or rewrite the failed artifact before the next stage proceeds. Cap7 should not skip generation because old refs exist unless the user explicitly asks to reuse existing artifacts, and reused artifacts still need gate review. This preserves the guarantee that final database fields came from current raw sources, current code context, and passed semantic review.

Path hygiene is also a hard constraint. Generated target-project artifacts must not expose local home directories, usernames, skill installation paths, temporary paths, or absolute paths outside the target repo root. Reports can mention local worktree paths for immediate user operation, but published planning refs should use target-repo-relative paths or conceptual references.

# known-limits

This workflow depends on the target project providing a usable t2p skill. If `.agents/skills/t2p/SKILL.md` is missing in the issue worktree, capability 2 stops. That is safer than inventing requirement sources, but it means IntentMill cannot currently plan arbitrary repositories unless they adopt the expected t2p contract.

The workflow relies on host LLM judgment for cap3 through cap6 generation and cap11 semantic review. It contains detailed rubrics and required shapes, but it cannot mechanically prove that the agent read enough code or that a gate decision is substantively correct. The protection is procedural: mandatory evidence reading, targeted review loops, and explicit revise handling.

The worktree setup rules assume a Git branch-per-issue model and a configured default branch. For NSDK, `staging` may be used as a default fallback when the config is missing, but other projects require explicit default branch configuration. Rebase conflicts, dirty base clones, and dirty unrelated issue worktree files are reported as blockers rather than automatically resolved.

The workflow does not include a retry or recovery strategy for transient target-project t2p failures, Git network failures, or missing raw requirement evidence. It stops and reports the blocker or records source limitations in generated artifacts. Backend run timeout handling belongs to the Codex run service, not this workflow.

# notes-for-ai

When changing this module, start by identifying which runtime path consumes the affected rule. Output shape changes should be checked against the Codex run service's artifact reader, estimation parser, gate decision parser, and Git sync restrictions. Sequencing or capability-boundary changes should be checked against cap7 because it is the orchestrator that the UI-triggered server prompt asks Codex to run.

Preserve the distinction between IntentMill root, base target clone, and issue worktree. Most mistakes in this module would not be type errors; they would be operational mistakes that write files in the wrong repo or allow server persistence from the wrong evidence. Any new capability that reads or writes issue-specific files should say exactly which working directory it runs in and which paths it may touch.

Keep generation artifacts narrow and role-specific. If a future ticket needs additional planning material, add a clearly named capability or artifact contract rather than overloading `im-solution.md` or `im-ac.md`. The server currently persists only the summary, solution, criteria, and estimation fields, and it uses `im-gate.md` as the readiness signal.

Treat cap11 as part of the product contract, not as editorial polish. If you add new artifact fields or new artifact types, update the gate checks so readiness still means the next actor can proceed without rediscovering basics. Also update tests or manual verification around backend-triggered runs when gate wording or estimation formatting changes, because server parsing depends on stable human-readable structures.
