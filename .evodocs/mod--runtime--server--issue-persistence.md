# purpose

The `runtime/server/issue-persistence` module owns IntentMill's local PostgreSQL state. It creates and qualifies database tables, manages the shared connection pool, defines issue and estimation TypeScript shapes, reads and updates issue rows, clears local project/cycle rows, and computes planning completeness metrics. It is the canonical local store for issue facts imported from Linear and planning artifacts generated by IntentMill.

This module is deliberately narrower than all server persistence side effects. It does not fetch Linear, spawn Codex, parse `.t2p` artifacts, or decide whether a planning run is ready. Instead, it provides the schema and issue operations those other services rely on. Linear sync writes observed issue facts and snapshots through this storage layer. Codex runs write generated planning fields through `updateIssue` after their own gate and Git checks. The UI and CLI read or mutate rows through these services.

The module's central product contract is the `issues` row. A row combines Linear-observed fields such as title, assignee, sprint, status, description, comments, and extra metadata with IntentMill-owned fields such as summary, solution, criteria, and estimation. Future work that changes this table must account for every producer and consumer of those fields.

# structure

Database client behavior lives in the DB client area. A singleton `pg` pool is built from resolved runtime config, and SSL is enabled when the configured sslmode is `require`. `withClient` wraps acquisition and release so callers do not leak clients. `closePool` resets the initialization promise and ends the pool, which is important for one-shot CLI commands. Table names are built with the configured schema and quoted identifiers.

Initialization is guarded by a shared promise. The first caller creates the configured schema, creates or replaces a UTC updated-at trigger function, sets the search path, and applies the schema SQL. If initialization fails, the promise is cleared so a later attempt can retry. This allows UI requests, CLI commands, sync, and run persistence to all call `initDb` without racing separate setup attempts.

The schema source creates three tables. `issues` is the current local issue state and planning field store. `sync_runs` records Linear sync executions and their stats. `issue_snapshots` stores per-sync copies of issue observed fields and metadata, tied to sync runs by a cascading foreign key. Both issue and snapshot tables receive the UTC updated-at trigger.

The schema also contains compatibility cleanup. It ensures `project` exists on `issues` and `issue_snapshots`, drops old `dm_*` planning fields, drops and recreates the `im_estimation` JSON check constraint, and drops `im_estimation` when an older non-jsonb column exists. This makes startup schema application both creation and lightweight migration for the current local database.

Issue service behavior is built around explicit column lists. `ISSUE_COLUMNS` defines what every issue read returns. `UPDATEABLE_FIELDS` defines what `updateIssue` can write. Sprint normalization accepts bare cycle numbers and case/spacing variants such as `cycle 19`, producing `Cycle-19`. Type definitions describe JSON values, issue rows, update patches, filters, estimation objects, and planning metrics.

# flows

The initialization flow starts before any query or update. Issue service methods call `initDb`, which runs through the guarded client initialization path. The runtime config provides the PostgreSQL connection and schema name. After initialization, all SQL uses schema-qualified table names, so the configured schema remains the namespace boundary even if the search path changes elsewhere.

The issue list flow builds a parameterized query from optional filters. A project filter matches rows where `project` equals the requested value or where `project` is null. This keeps older or unscoped rows visible in project-specific views. Assignee, sprint, status, and version filters are exact matches, with sprint normalized first. The service clamps limit to 1 through 1000, clamps offset to zero or above, orders by sprint, status, assignee, and issue id, and returns typed rows.

The clear flow is scoped and destructive. It requires a non-empty project, normalizes the sprint, deletes issue rows where project matches or is null and sprint matches, and returns the normalized project, normalized sprint, deleted count, and deleted issue ids. This is the persistence operation behind the UI Clear button. It does not delete sync runs, snapshots, JSON exports, run logs, or target worktree artifacts.

The update flow applies direct row patches. Undefined patch values are ignored, unknown fields are ignored, and only fields in the update allowlist can be set. If no effective entries remain, the service returns the current row instead of issuing an empty update. Otherwise it constructs a parameterized SET clause, updates by issue id, and returns the updated row or null. This supports both gated Codex persistence and manual CLI repair, so callers must enforce their own higher-level readiness rules.

The metrics flow counts planning completeness for a sprint or the whole issue table. Total is all matching rows. Missing summary, solution, and criteria count rows where the corresponding text field is null or blank after trim. Missing estimate counts rows where `im_estimation` is null. These metrics are used by dashboard-style views to show which planning artifacts are still absent.

The sync state flow is partly owned by other modules but stored here. Linear sync inserts `sync_runs` and `issue_snapshots` inside a transaction. Snapshot rows capture observed issue state at sync time, while current rows in `issues` remain the UI's active view. This module supplies the schema and table qualification that make those writes possible.

# module-relationships

The module depends on server config for PostgreSQL connection details and schema name. It does not parse environment variables or `ssot-config.json` itself. That keeps credential resolution centralized while persistence owns how those settings are used for pooling, schema creation, and table qualification.

The planning UI is a read and clear consumer. It lists issue rows for project/cycle views, shows generated planning fields, and deletes local rows through clear behavior. The UI does not write issue fields directly; it calls server functions that delegate here.

Linear sync is a major writer. It upserts observed Linear fields into `issues`, detaches stale rows from a cycle, creates a sync run, and writes snapshots. It intentionally does not overwrite `im_summary`, `im_solution`, `im_criteria`, or `im_estimation` during upsert, because those fields are generated by IntentMill rather than read from Linear.

Codex runs are the gated planning-field writer. After a successful ready gate, artifact parsing, and Git sync, the run service calls `updateIssue` with generated summary, solution, criteria, and estimation. This module enforces only update allowlists and database constraints; the run service enforces artifact readiness.

The CLI is a local operator consumer and writer. It can initialize the database, print schema SQL, list/show rows, and call `updateIssue` manually. That relationship is useful for repair and inspection but bypasses the run service's gate, so manual CLI changes should be treated differently from generated artifacts.

# constraints

Preserve schema qualification and identifier quoting. Every table reference should go through `tableName` or the schema initialization context. Direct unqualified table names in service SQL can accidentally read or write the wrong schema when local config changes.

Keep update allowlists explicit. `updateIssue` should not accept arbitrary object keys as SQL columns. Adding a persisted field requires updating schema SQL, TypeScript types, returned column lists, update allowlists when writes are intended, and every producer/consumer that owns the field.

Maintain project-or-null behavior deliberately. List, sprint listing, and clear treat `project IS NULL` rows as matching a project filter. This supports older or unscoped data, but it also means clear can delete null-project rows for a selected sprint. Any change to this behavior affects UI rows, CLI commands, and data cleanup semantics.

Treat estimation as a cross-module contract. The JSON schema, SQL check constraint, TypeScript `IssueEstimation`, Codex run Markdown parser, CLI update JSON, and UI estimation cell all expect compatible fields. The current SQL check is less strict than the JSON schema, so changes should either align them or preserve the intentional difference with tests.

Do not let persistence decide generation readiness. The database can reject malformed estimation shape, but it cannot know whether summary, solution, or criteria are semantically valid. Gate and artifact quality belong to the Codex run service and agent workflow. Persistence should remain a storage boundary, not a review engine.

# known-limits

Schema changes are applied by startup DDL rather than an ordered migration history. The current SQL handles some compatibility cleanup, but there is no versioned migration table or rollback path. Complex data migrations would need explicit additional handling.

Timestamps are stored as UTC-formatted text rather than native timestamp columns. This keeps values simple for display and JSON output, but it limits database-native time operations and type checking.

The estimation JSON check does not fully match the JSON schema file. The schema file rejects additional properties and requires hours to be at least one. The SQL check only requires an object with required keys, allowed mode, numeric hours, and string rationale. The parser also accepts non-negative hours. This drift is a maintenance risk.

Manual CLI updates can write planning fields without a ready artifact gate. That is intentional local repair power, but it means not every `im_*` value in the database is necessarily produced by the Codex run service.

# notes-for-ai

When changing issue fields, start from the schema and then follow the field through types, column lists, update allowlists, Linear sync upsert behavior, Codex run patch construction, UI table projection, CLI update options, and tests. Missing one of those surfaces commonly creates silent null fields or failed updates.

When changing estimation, update every representation together. Check `im-estimation.schema.json`, SQL check constraints, `IssueEstimation`, `parseIssueEstimationMarkdown`, CLI JSON update examples, UI estimation rendering, and tests that reject invalid estimation. Decide explicitly whether SQL, JSON schema, and parser rules should become stricter or remain different.

When changing query filters, preserve parameterized SQL and limit clamping. Be especially careful with project-or-null semantics because it affects visibility and deletion of older rows. Add tests or manual SQL checks for null project rows if that behavior changes.

When adding database work, prefer adding storage behavior here and keeping external effects elsewhere. This module should not call Linear, spawn Codex, inspect target worktrees, or perform Git operations. Other server modules can call issue persistence after they have enforced their own external contracts.
