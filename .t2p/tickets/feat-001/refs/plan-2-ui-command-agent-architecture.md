# Plan 2: UI Command Composer and Codex-Executed AI Workflows

## Decision

IntentMill should be an AI-native sprint planning workspace with a lightweight UI. The first implementation should not embed a heavy agent runtime in the web app. Instead, the UI should compose precise, copyable commands or Codex prompts, and the user should run them in Codex.

This keeps AI as the main planning engine while avoiding premature UI complexity around process execution, permissions, streaming logs, cancellation, retries, workspace selection, and secret handling.

## Product Shape

The UI is a planning cockpit:

- show sprint state, issue lists, planning gaps, sync history, and AI workflow readiness;
- explain what each AI workflow will read and write;
- generate a copyable command or Codex prompt for each workflow;
- refresh and display results after Codex writes artifacts or updates the database.

Codex is the AI executor:

- runs the workflow command or prompt in the repository;
- performs LLM-heavy reasoning such as summaries, implementation plans, estimates, dependency analysis, and release recommendations;
- writes only through approved local service functions or workflow helpers;
- reports verification results back to the user.

Server code is the deterministic boundary:

- owns DB access, schema, Linear sync, snapshot diffing, and field preservation rules;
- exposes one canonical service layer used by UI, scripts, and skills;
- prevents AI workflows from bypassing local write rules or writing to Linear without explicit approval.

## Architecture Principle

UI, scripts, and skills must not implement separate versions of the same workflow. Each workflow should have one canonical implementation path.

For example, refreshing summaries should ultimately call one service/workflow path whether it is started from:

- a copyable command generated by the UI;
- a Codex prompt;
- a project skill;
- a future local runner.

The UI can compose commands, but it should not own planning logic.

## First-Phase Flow

The first phase should implement UI as a command composer.

For each AI workflow, the UI should show:

- workflow name;
- target scope, such as `Cycle-18` or `ENG-506`;
- reads;
- writes;
- explicit non-goals;
- copyable command;
- copyable Codex prompt when natural-language execution is more appropriate.

Example summary workflow card:

```text
Workflow: Refresh summaries
Target: Cycle-18
Reads: latest two sync runs, current issues, descriptions, comments
Writes: issues.dm_summary only
Never writes: Linear, dm_solution, dm_criteria, dm_estimation
Command:
npm run intentmill -- ai summary --sprint Cycle-18
```

Example solution workflow card:

```text
Workflow: Draft solution
Target: ENG-506
Reads: issue context, selected code repository, selected docs
Writes: issues.dm_solution only
Never writes: Linear, source code, dm_summary, dm_criteria, dm_estimation
Command:
npm run intentmill -- ai solution --issue ENG-506 --code <path> --docs <path>
```

Example Codex prompt variant:

```text
请在当前 IntentMill 仓库运行 summary workflow：
- sprint: Cycle-18
- collect changed tickets and tickets missing dm_summary
- generate concise Chinese summaries
- write only issues.dm_summary
- do not write to Linear
- run verification and report changed issue ids
```

## Workflow Contract

Each AI workflow should be split into clear phases:

1. `collect`: deterministic code reads DB, snapshots, source files, or configured inputs and writes an inspectable artifact.
2. `generate`: Codex/LLM performs semantic work and produces a draft artifact.
3. `apply`: deterministic code validates the artifact and writes only approved local fields.
4. `verify`: deterministic checks confirm what changed and that forbidden fields were not touched.

The LLM should do semantic reasoning. Code should do parsing, validation, DB writes, diffing, and exact checks.

## Recommended Workflow Set

Initial workflows:

- `sync`: fetch Linear sprint data and record `issues`, `sync_runs`, and `issue_snapshots`.
- `summary`: generate or refresh `dm_summary`.
- `solution`: draft `dm_solution` for one issue from issue context plus code/docs paths.
- `criteria`: draft `dm_criteria`.
- `estimate`: draft or review `dm_estimation`.
- `release-plan`: propose first-week and second-week release candidates with reasons.
- `dependency-plan`: identify ordering constraints and blockers.

Only low-risk deterministic workflows should become direct UI actions early. Good candidates:

- list issues;
- update local estimate;
- edit local planning text;
- trigger Linear sync if credentials are configured and the operation is clearly local-read only.

LLM-heavy workflows should start as copyable Codex commands/prompts.

## Future Local Runner

After command-based workflows stabilize, IntentMill can add a lightweight local runner. It should execute only white-listed workflows, not arbitrary shell commands.

Runner constraints:

- no arbitrary shell input from the browser;
- workflow ids and typed parameters only;
- no secrets returned to the frontend;
- execution records stored in a `runs` or `workflow_runs` table if persistence is needed;
- cancellation/retry behavior explicit;
- failed runs should show a copyable Codex fallback command;
- output should be summarized and linked to artifacts rather than streamed as raw terminal logs by default.

This runner is optional and should not block the migration.

## Avoid for First Version

Do not build a full UI-driven Codex exec bridge in the first migration slice.

Avoid:

- browser-submitted arbitrary commands;
- free-form shell execution;
- embedding a long-running agent runtime in the app;
- exposing raw environment variables or config values;
- duplicating Codex behavior in UI code;
- writing to Linear from an AI workflow without an explicit separate review and approval step.

## Data and Safety Rules

AI workflows may update local planning fields only through approved apply steps:

- `dm_summary`
- `dm_solution`
- `dm_criteria`
- `dm_estimation`
- future explicit planning fields

AI workflows must not silently overwrite observed Linear facts:

- `title`
- `description`
- `comments`
- `status`
- `assignee`
- `parent_issue_id`

Linear write-back is out of scope for the first phase. If added later, it must be a separate reviewed workflow with an explicit confirmation boundary.

## UI Implications

The frontend should prioritize:

- clear workflow cards;
- copy buttons;
- visible read/write boundaries;
- latest run/sync status;
- missing planning field counters;
- issue detail views with local AI fields;
- result refresh after Codex execution.

The frontend should not attempt to hide the fact that Codex is the executor. The product model is: IntentMill prepares context and commands; Codex performs AI work; IntentMill stores and reviews the results.

## Acceptance Criteria

- The UI can generate copyable commands/prompts for core AI workflows.
- Each generated command states target, reads, writes, and forbidden writes.
- Workflow implementation has collect/apply boundaries instead of direct uncontrolled LLM writes.
- UI and project skills call the same underlying workflow helpers.
- No first-phase feature requires arbitrary shell execution from the browser.
- Local DB and Linear sync rules remain enforced by server-side TypeScript code.
